Prepared on 14 September 2026 and updated on 15 September 2026. This record describes what this public repository proves and where the proof stops. The repository is a curated copy of a reviewed local package. Some results below were measured on the repository's own files. The others are dated results from the reviewed package, and each section says which kind it is.

## Semantic and recovery evidence

The final tests exercise exact transaction, receipt, log and block identity checks for action setup, ERC-20 approval, mandate grant, execution and revocation. They also exercise expected state, balance, allowance and cumulative-use changes. Receipt status by itself is insufficient.

Recovery fixtures cover pending, signed, broadcast or uncertain, confirmed and semantically verified journal states. They cover duplicate operation binding, full decoded signed-transaction matching, signed-byte identity, nonce conflicts, unresolved broadcasts, confirmation block-hash changes and restart behavior. An unresolved nonce cannot receive a replacement signature, and only identical signed bytes are eligible for a resend.

These semantic and recovery checks use injected fixtures. The test suite does not load a real wallet, create a real signature, call a live RPC endpoint or broadcast a transaction. The live path can do those things only when started with --live, and it was started that way for one run on 15 September 2026, described below. Fixture bytes and local hashes are not claimed as live Ethereum transaction hashes. The live run carries the independently built expectation of every write, fresh observations from two read sources and the semantic checks after each confirmation, and its signed bytes stay local.

## Live Sepolia path

The code of a live Sepolia run is in this repository. It was implemented on 14 September 2026 and audited the same day as round A1, which found eleven defects in recovery, locking, two-source verification, control evidence, cleanup, export completeness and recording metadata. Every finding was fixed with an acceptance test that fails on the audited source and passes on the fixed one, and the suite grew from 313 to 336 tests. A second audit on 15 September 2026 ran the suite twice, replayed the eight root reproductions of round A1 against the fixed source, read every fix against the source and reviewed the path adversarially. It found one low defect, the launcher's argument quoting for a wallet directory that ends in a backslash, and one test assertion that could not fail. Both are fixed in this repository.

An independent re-check of the fixes on 15 September 2026 left three findings open and recorded two design decisions. The lock still compared a record and then acted on the file name in a second step. A recheck of a verified write kept it as a basis for the next write when its depth had fallen below the required two on one source. A control block whose hash one source reported as changed stayed canonical when the other source had no block at that height. The grant verifier rejected a second grant on the same agent and principal pair, so a repeat run stopped after the grant was on chain and cleanup could not revoke it. The code identity hash was stored with a run but never compared again.

A third round on 15 September 2026 implemented all of that. The three live lock files are held through an exclusive file handle that the operating system keeps for the life of the holding process, so a stale takeover or an old release cannot remove a newer holder, and nothing in the protocol compares a record and then acts on the path. Ownership and the source code identity are checked again right before every preparation, signature and send, after the reads that precede them. A dependent write waits until both read sources return every earlier write of the run at the required depth. A control or write block that one source reports with another hash is withdrawn even when the other source has no block at that height, and a missing block never counts as agreement. A grant after a revoked mandate of the same pair verifies from the registry's real state, and cleanup revokes only a mandate it can attribute to the run by receipt, calldata, event and block-bound state on both sources. The owner approves two hashes, the exact plan and the stable identity of the source code, which covers the sorted file table of src, public, tools, the live proposal, the vendored ethers bundle and package.json. The owner, agent and signer processes each compute that identity when they start and refuse a run whose approved identity differs from their own or from the files on disk. A live recording binds to the exported evidence package by the hash of its checksum file. Two independent checks read the round before it was closed. One found that the recording binding and the evidence export ran the completeness rule without checking the code identity, so a process whose files had changed after the run could still bind a recording or export a package. Both now refuse, and the export names the identity it ran with. The suite grew from 336 to 363 tests. The eight root reproductions of round A1 and the counter-tests of the re-check were replayed against this tree, and none of the old behaviour reproduces.

An independent re-check of the third round on 15 September 2026 confirmed the handle-bound lock, the depth gates, the grant state machine and the code identity binding, and left five findings open. A retry of an execute whose preparation was recorded before a failed signature skipped the control check and signed after the control block had been reorganised. Cleanup reset a newer allowance that the principal had granted to the same executor after the run, because only the run's old approve was proven. A code identity mismatch blocked even the read-only tracking of a transaction that was already on its way. The recording binding checked only the transaction table against the checksum file, so a damaged receipt or a package exported before a write was re-mined into another block was still accepted. The signer compared its code identity only at startup. A fourth round the same day implemented all five with a test for each. The control check runs before the first execute signature whether or not a preparation exists, and a control withdrawn before any execute bytes exist is observed again by the owner. Cleanup resets an allowance only when the value on chain equals what the run's approve and its verified execute leave behind, and names any other value instead of resetting it. A process without the approved identity follows a broadcast transaction to its receipt by reads, records the receipt, marks no semantic result and stops naming the mismatch and the state each step reached. The recording binding requires every member of the package, checks each against its checksum and compares every write's block, every control observation and the finality statement with the run as it is now. The signer's request handler moved into its own module and compares the approved identity with the process and with the files on disk inside its serialized queue, right before every preparation, signature and send. Two independent checks read the round before it was closed. The adversarial one found that the control check ran once when a phase began and not again before the signature, so a control block reorganised during the reads that precede the signature was still signed on. The executor now reads every control a step rests on from both sources right before the step's bytes are signed, in setup and in revocation alike, and cleanup writes are the one exception because they claim no control evidence. The suite grew from 363 to 377 tests. The re-check's own reproductions were replayed against this tree with their expectations unchanged: the pending retry stops with the control withdrawn and signs nothing, the foreign allowance stays in place and is named, the expired resume under a changed source reads the chain and stops naming the mismatch, and the damaged and the stale package are both refused. The eight root reproductions of round A1 still pass.

An independent re-check of the fourth round on 15 September 2026 confirmed the pending retry, the read-only tracking, the package integrity and the signer's queued identity check, and left two findings open. The control reading of the fourth round ran before the signing step, and the signing step itself still read the nonce twice after it, so a control block reorganised during those last reads was still signed on. Cleanup compared the allowance on chain with the value the run's writes leave behind, so a later independent approval of exactly the same amount was still reset. A fifth round the same day implemented both with a test for each. The controls a step rests on are read from both sources inside the signing step, after the last nonce reads and the decision whether to prepare again, right before the signer is asked. Ownership and the code identity are checked once more at the same point, and cleanup keeps its exemption because its writes claim no control evidence. Cleanup now reads the approval events of the owner and spender pair from the run's approve block to the block its reads use, on both sources, through a new bounded event query of the read client: the sources must agree, the run's own approve must be present in its recorded block, and every event must belong to a transaction the run signed. A foreign event, a disagreement or a source that cannot answer leaves the value in place and names the reason. The recording binding names the package's own finality reading time beside the run's current one, as the re-check decided. The suite grew from 377 to 388 tests. Two independent checks read the round before it was closed. The adversarial one found that the origin was read once at the cleanup decision and the reset was still signed later, so an approval that landed in between would have been wiped, and that the event query accepted logs outside its filter. The origin is now read again right before the reset is signed, and a log outside the requested address, range or topics is refused as a provider fault. The re-check's own reproductions were replayed against this tree with their expectations unchanged: the control block replaced during the last nonce read leaves execute, revoke and approve reset unsigned and pending, and the later approval of the same amount stays in place with the reason named. The eight root reproductions of round A1 still pass. An independent re-check of the fifth round on 15 September 2026 closed both findings on that tree and recorded three refinements for the next round: the wording of the observation window between the last block-bound check and the inclusion of the reset, the public list of the cleanup evidence names and their originReason values together with their export into the package, and one definition of the event query's range limit. The tests use a fake chain and a fake gateway. The repository holds no signed transaction, no wallet and no API key.

## The live run of 15 September 2026

The first live run was made on Erik's decision on the tree of the fifth round, before its external re-check was in. Erik funded the principal and the agent from public faucets, approved every plan in chat by naming its approval hash and its code identity hash, and started the signer process himself with both hashes. The session that drove the owner server never held a key, a keystore or the API key. Three attempts stopped before any signature at the first Brickken preparation. The parser read the documented x402Requirements quote of the preparation response as a payment demand, then it accepted the quote only as an object while the sandbox sends a list, then an undocumented top-level executionMode echo failed its exact key set. Each correction produced a new code identity, a new plan and a new approval. The parser now reads the quote as data in any JSON form, keeps it out of the transaction and the preparation hash, never acts on it and never pays. It admits the echo only with the value client-signed, and the signer records the structure of a rejected response, key names and JSON types without values. The fake gateway of the tests now sends both fields in every response, because none of the earlier audits could see a field the fixture never produced. The suite grew from 388 to 390 tests.

The fourth attempt, run `live_c990e8a178b04a35835d8fe92097c20f`, completed. Its approval hash is `9a2e5ee17d8bed85d30046529acc20f590be2d1bb06b6aa13e71f66228544fcb` and its code identity is `086c78401b54a9f9d9f6a47018b4ed6e0e04038e5a5c708d685b06443d31dc79`. The owner signed setAction, the ERC-20 approval of 15000 raw units and the grant, the agent executed a transfer of 10000 raw units to the synthetic recipient through the MCP tool execute_approved, and the owner revoked the mandate and reset the allowance to zero. The six transactions were confirmed in blocks 11708599, 11708602, 11708605, 11708611, 11708618 and 11708714 with the same block hash on both read sources, and every receipt has status 1. The four controls passed: the transaction cap at block 11708606, the cumulative cap and the state before the revocation at 11708614, and the state after the revocation at 11708621. A second call of execute_approved with the same operation id at 12:23 UTC returned the recorded result without a new signature: the agent's nonce had not moved and the principal's balance matched the postcheck, and the observation is in the package as `replays/replay-1.json`. The finality rule requires every block of the run to be reported as finalized by both read sources. The secondary source reported all ten blocks of the writes and the controls as finalized within its normal delay of about seventy blocks. The primary source, publicnode, reported the same finalized block 11703676 from before the run in every reading from 08:28 UTC to 11:26 UTC on 15 September 2026, with a block timestamp of 15:10 UTC on 14 September, and its safe block stood at 11703708 for the same period, so its consensus view had stopped the day before the run. A third source read outside the run, 1rpc.io, agreed with the secondary source. The source was not replaced during the run, because the endpoint list is part of the code identity. A first package was exported at 11:26 UTC with the incomplete flag after Erik's decision to wait thirty minutes more. At 12:12 UTC the primary source reported finalized block 11709728, the same as the secondary source, and the run's finality reading recorded all ten blocks of the writes and the controls as finalized on both sources. The package was exported again with that reading and the replay observation, and it is complete under the run's own rule.

The revocation phase stopped seven times before a signature with HTTP 429 from one public read source, whose burst limit the preparation of the allowance reset exceeded with its dependency reads. The read client fails closed on 429 by design, and the code could not change during the run because the code identity binds the run to the tree. On Erik's decision the owner server was restarted with a Node preload that spaces the reads to the two public endpoints and retries a read that answers 429, and never retries a send. The preload is outside the code identity. The process identity and the disk identity of the run were unchanged, and the signer process was not restarted. The owner server process also executed that file during the last step. That is a deviation from the statement that the process runs the approved bytes, and it is disclosed here rather than corrected after the fact. The proper correction, bounded backoff on reads and spaced dependency reads inside the covered code, belongs to the next fix round.

The evidence package is `verification/sepolia-live-c990e8a178b0/`, 32 files exported by `tools/export-live-evidence.mjs` from the owner's data directory with `SHA256SUMS.json` over every member (SHA-256 of that file `a367dea097bc7f96f41defeea5816d708e0653104994b6e4979eef4b830b96e7`). It holds the run approval, the preflight and code identity records, the preparation of every write with its receipt and its postcheck, the four control observations, the replay observation, the finality reading and the transaction table with explorer links. The incomplete export of 11:26 UTC was replaced by this one and is not in the repository. The export refuses any file that would carry signed transaction bytes, and the package was checked before publication: it holds no signed bytes, no wallet and no key, and every address in it belongs to the plan. The preparation evidence of setAction carries the x402Requirements quote the API returned, three priced assets, which is pricing information and not a secret.
